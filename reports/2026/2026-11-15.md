## 🔥 1. Top 5 — Must Know

### 1. NEW — GitHub Secret Scanning detects Cloudflare Access service tokens (12 Nov 2026)
- **What happened:** GitHub added detection for `cloudflare_access_service_token` in repository secret scanning.
- **Why it matters:** Cloudflare Access service tokens used by deployment automation, internal APIs and Zero Trust integrations can be accidentally committed. This new detector improves coverage, but the announcement does not claim push protection is enabled by default for this token type.
- **Who:** DevSecOps, CI/CD maintainers, Cloudflare Access users, platform engineers.
- **Maturity:** Production Ready (detector available).
- **Recommendation:** Try — audit any Cloudflare Access credentials used in repositories or CI pipelines; rotate any exposed tokens.
- **Effort:** 20–45 minutes for initial audit.
- **Primary source:** https://github.blog/changelog/2026-11-12-secret-scanning-adds-a-detector-for-cloudflare/

## 🆕 2. New Tools Worth Trying

**Gitleaks** (https://github.com/gitleaks/gitleaks): established OSS CLI for scanning Git repositories and history for hardcoded credentials; useful when GitHub's licensed scanning capabilities are unavailable. **Maturity:** Production Ready / established OSS. **Recommendation:** Try. **Evaluation:** 20–40 minutes.

**TruffleHog** (https://github.com/trufflesecurity/trufflehog): open-source secret discovery with verification support for some credential types; assess scope and avoid exposing real credentials during testing. **Maturity:** Established OSS. **Recommendation:** Try in an isolated test repository. **Evaluation:** 30–60 minutes.

These are tool discoveries, not newly released projects.

Use Gitleaks as a fast, local or CI-integrated secret detection layer, especially for GitLab/Jenkins pipelines. It does not replace credential rotation or cloud-provider detection and cannot guarantee every token type is recognized.

Source: https://github.com/gitleaks/gitleaks

## 🧪 Try This Today

Run Gitleaks on a disposable repository with dummy secrets, inspect its findings and false positives, then consider adding a non-blocking scan to GitLab CI before enabling a blocking policy. Do not create or commit live credentials for testing.
